# Kaew — เป้าหมายผลิตภัณฑ์และเกณฑ์ยอมรับ

สรุปข้อกำหนดที่ยังมีประโยชน์จากร่างโครงการ เป้าหมายด้านล่างยังไม่ใช่ผลทดสอบหรือรายการที่ทำครบแล้ว สถานะจริงดู [README](../README.md) และ [checkpoint](CHECKPOINT_CRITICAL_PATH.md). แผนปัจจุบันตัด flow sensor และการผสมน้ำ/ควบคุมอุณหภูมิออกแล้ว; ตรวจการจ่ายผิดปกติจากน้ำหนักและเวลาแทน (ยังต้องทดสอบ).

## แนวคิดหลักตามร่าง

**AI Smart Water Dispenser** — เครื่องจ่ายน้ำขนาดเล็กวางข้างคอมพิวเตอร์ มีผู้ช่วยเสียงภาษาไทยชื่อ “แก้ว”

- ตรวจว่ามีแก้ว วัดน้ำหนัก และประมาณปริมาณน้ำหลัง calibration/tare
- จ่ายน้ำโดยใช้มิลลิลิตรเป็นหน่วย AI ปรับเป้าหมายปริมาณน้ำในแก้วและเวลาเตือน โดย controller ตรวจขอบเขตและเงื่อนไขก่อนนำไปใช้ หยุดเมื่อยกแก้วออก
- รับคำสั่งเสียงไทย เช่น เติม 200 มล. เติมครึ่งแก้ว หยุด และถามปริมาณน้ำคงเหลือ พร้อมตอบด้วยเสียงไทย
- จ่ายน้ำอุณหภูมิห้อง โดยตัดการทำน้ำอุ่น ถังน้ำร้อน ชุดผสมน้ำ และคำสั่งตั้งอุณหภูมิออกจากขอบเขตที่กำลังพิจารณา
- ติดตามระดับน้ำในขวด ค่าน้ำที่เลือก และเหตุผิดปกติ; ไม่มี dedicated conductive leak sensor ในรายการล่าสุด จึงยังไม่อ้างว่าตรวจน้ำรั่วอัตโนมัติได้
- ใช้โมเดลผ่าน API ประเมินประวัติพฤติกรรมเพื่อปรับเวลาเตือนและเป้าหมายปริมาณน้ำ ไม่อ้างว่ามีการฝึกโมเดลส่วนตัวหรือปรับน้ำหนักโมเดลอัตโนมัติแล้ว
- มี dashboard, ประวัติ, cloud storage และ notifications ผ่าน Telegram
- ผู้ใช้ต้องการให้วางแก้วกลับแล้วเติมอัตโนมัติ โดยรายละเอียดการเปิดโหมดและ interlocks ยังต้องออกแบบ

## คุณภาพ AI ที่ต้องการ — เกณฑ์ทดสอบที่เสนอ

ความต้องการที่ผู้ใช้ยืนยันคือ AI ต้องฉลาดพอสมควร รายการต่อไปนี้เป็นข้อเสนอเพื่อคุยต่อ ยังไม่ใช่เกณฑ์ผ่านที่ผู้ใช้ยืนยันหรือความสามารถที่พัฒนาแล้ว:

- **เข้าใจภาษาไทยหลายรูปประโยค:** เช่น “เติมอีกนิด เอาแค่ 50 มล.” ต้องตีความเป็นเติมเพิ่ม 50 มล. และแยกจาก “เติมให้ถึง 50 มล.” ได้
- **ตามบริบทและการแก้คำสั่ง:** เช่น “เติมให้ถึง 200 มล.” แล้วแก้ว่า “เอาแค่ 150 พอ” ต้องจัดการคำสั่งล่าสุดร่วมกับปริมาณที่มีจริง โดยไม่เติมเกินเป้าหมายใหม่ หากเติมไปเกินแล้วต้องบอกตรง ๆ
- **ถามเมื่อกำกวม:** เช่น “เติมอีกหน่อย” โดยไม่มีปริมาณหรือค่าที่ตกลงไว้ ต้องถามให้ชัดก่อนเปลี่ยนปริมาณจ่าย
- **ใช้ข้อมูลจริงและอธิบายเหตุผล:** ตอบเรื่องค่าน้ำจาก sensor data พร้อมเวลา และอธิบายการปรับเวลาเตือน/ปริมาณโดยอ้างอิงประวัติหรือ feedback ที่ระบบส่งให้; เมื่อข้อมูลขาดหายต้องบอกว่ายังสรุปไม่ได้
- **ปรับตัวจากประวัติและ feedback:** ประเมินด้วยสถานการณ์ที่มีข้อมูลต่างกันและเปรียบเทียบผลกับพฤติกรรมคงที่ โดยวัดทั้งความเหมาะสมของข้อเสนอและความสม่ำเสมอ การเก็บประวัติเป็นหน้าที่ของระบบและต้องส่งบริบทให้โมเดล ไม่สมมติว่า API จำเองหรือฝึกตัวเองแล้ว

ก่อนเลือกโมเดล/voice pipeline ให้ทดลองตัวเลือกด้วยชุดสถานการณ์ภาษาไทยเดียวกัน รวมข้อความที่ถอดจากเสียงผิด คำสั่งกำกวม และข้อมูลเซนเซอร์ไม่พร้อม ประเมินความถูกต้องในการเข้าใจคำสั่ง/ตัดสินใจ ความอิงข้อมูลจริง เวลาในการตอบ และค่าใช้จ่าย เกณฑ์ตัวเลขและขอบเขตการคุยเรื่องทั่วไปยังไม่กำหนด ส่วนการหยุดปั๊มและ interlocks ยังคงทำงานที่ controller โดยไม่รอโมเดล


## M7 — ความปลอดภัย (ยืนยันแนวทางแล้ว ยังไม่ทดสอบเครื่องจริง)

ผู้ใช้ตอบตกลงกับแนวทางความปลอดภัย 8 เรื่องระหว่าง refinement วันที่ 30 ตุลาคม 2026: แยกน้ำออกจากวงจรพร้อมถาดรอง, ตรวจแก้วและหยุดเมื่อยกออก, จำกัดปริมาตรป้องกันล้น, หยุดเมื่อ flow ผิดปกติหรือจ่ายเกินเวลา, หยุดเมื่อยืนยันเงื่อนไขสำคัญไม่ได้, ปุ่มหยุดจริงที่ไม่รอ AI/Internet/Telegram, reboot ปั๊มปิดโดยไม่เติมต่อจากคำสั่งค้าง และทางน้ำ/วัสดุที่เหมาะกับน้ำดื่มพร้อมทดสอบการหยุดไหล ส่วนคำถามว่าจะใช้อะแดปเตอร์อย่างเดียวหรือมีแบตเตอรี่ยังไม่มีคำตอบเจาะจง จึงยังไม่ถือว่าเลือกแหล่งจ่ายไฟแล้ว

### กฎข้อ 4.3 ตามสำเนาโจทย์

- ไฟบ้าน 220 V AC: สวิตช์ผ่าน relay/SSR module ที่ปิดมิดชิดและได้รับการรับรอง หรือ smart plug ตามโจทย์เท่านั้น ไม่มีสายไฟบ้านเปลือย อุปกรณ์ที่ใช้ไฟบ้านต้องให้ TA/อาจารย์ตรวจตามกติกาก่อน demo ทั้งนี้ smart plug ไม่นับแทน actuator หลักตาม M2
- แยกของเหลว ปั๊ม และขวด/ถังน้ำออกจาก electronics ทางกายภาพ พร้อมถาดหรือ enclosure รองรับน้ำหก
- หากใช้แบตเตอรี่ลิเทียม ต้องมีวงจรป้องกันและไม่ปล่อยชาร์จโดยไม่มีคนดู
- ส่วนที่เคลื่อนที่ต้องมีวิธีหยุดอย่างปลอดภัย เช่น limit switch, timeout หรือ manual stop

ข้อเสนอสำหรับเครื่องตั้งโต๊ะนี้คือปั๊ม/วงจรภายในใช้ไฟ DC แรงดันต่ำผ่านอะแดปเตอร์สำเร็จรูปที่เหมาะกับโหลด เก็บส่วนไฟบ้านในส่วนปิดมิดชิดและห่างทางน้ำ รุ่น แรงดัน พิกัดกระแส และการใช้แบตเตอรี่ยังไม่เลือก ข้อเสนอนี้ไม่แทนการตรวจตามกติกาวิชา แนวทางตรวจอุปกรณ์ไฟฟ้าเพิ่มเติม: [HSE — Electrical safety FAQ](https://www.hse.gov.uk/electricity/faq.htm)

### แนวทางควบคุมและโครงสร้างที่ตกลงไว้

- Safety controller แยกจาก voice/AI; AI ห้าม override interlocks
- จำกัดปริมาตรสูงสุดและเวลาจ่ายสูงสุด ตรวจแก้วก่อนเริ่มและหยุดเมื่อยกออก
- หยุดเมื่อน้ำต่ำกว่าระดับที่กำหนด หรือข้อมูลเซนเซอร์ที่จำเป็นต่อความปลอดภัยเสีย/หมดอายุ รวมถึง node → gateway timeout ที่ทำให้ตรวจเงื่อนไขไม่ได้; การขาด Internet/AI/Telegram ต้องไม่ทำให้ข้าม interlocks และโหมดใช้งานต่อเมื่อ cloud ขัดข้องยังต้องกำหนด การตรวจจับน้ำรั่วอัตโนมัติยังไม่มีวิธียืนยันหลังตัด conductive leak sensor
- ยังคงแยกน้ำออกจาก electronics และมีถาด/ทางรองรับน้ำตาม M7 โดยไม่พึ่งว่ามี leak sensor หรือไม่
- มี emergency/manual stop และ actuator defaults ที่ปลอดภัยหลัง reboot
- เสนอ physical emergency stop ที่ตัดพลังงานปั๊มโดยไม่พึ่ง AI/cloud/software อย่างเดียว โดยวงจรจริงยังต้องออกแบบให้เหมาะกับปั๊มและพิกัดไฟที่เลือก
- หลัง reboot ให้ปั๊มปิดและไม่กลับไปทำคำสั่งเติมที่ค้างอยู่โดยอัตโนมัติ ต้องตรวจข้อมูล/เงื่อนไขใหม่ก่อนเริ่มงานใหม่
- ตรวจว่าปิดปั๊มหรือตัดไฟแล้วน้ำหยุดไหลจริง รวมถึงน้ำค้างท่อ/การไหลต่อจากการจัดระดับขวดและหัวจ่าย หากไม่หยุดต้องแก้ทางน้ำหรือเพิ่มอุปกรณ์ปิดน้ำที่เหมาะสมก่อนใช้งาน วิธีแก้ยังขึ้นกับรุ่นปั๊มและผลทดสอบ
- ไม่เปิด actuator จริงเป็นค่าเริ่มต้นระหว่าง simulation/พัฒนาช่วงแรก
- ตรวจเอกสารความเหมาะสมของชิ้นส่วนที่สัมผัสน้ำดื่ม รวมท่อ ปั๊ม ฝา หัวจ่าย และ probes พร้อมออกแบบให้ถอดล้างได้ รุ่นอุปกรณ์ยังไม่ยืนยัน
- ไม่อนุมานความจุแก้วจากการชั่งน้ำหนักครั้งเดียว

### หลักฐานที่ต้องมีสำหรับ Kaew

- รูป/ตรวจโครงสร้างจริง: ทางน้ำแยก electronics ถาดรอง ความมั่นคงของขวด/แก้ว การยึดท่อและสายไฟ และการตรวจไฟบ้านตามกติกาเมื่อมีส่วนที่เกี่ยวข้อง
- ทดสอบไม่วางแก้ว ยกแก้วระหว่างเติม น้ำต่ำ/หมด และเติมถึงปริมาตรสูงสุด โดยกำหนดค่าขีดจำกัดจากแก้วและอุปกรณ์จริง
- ทดสอบ flow ไม่มา จ่ายเกินเวลา เซนเซอร์ที่สำคัญอ่านไม่ได้/ข้อมูลค้าง และ node link หาย โดยบันทึกสถานะปั๊มและเหตุหยุด
- ทดสอบปุ่มหยุดแยกจาก software, reboot/ไฟกลับมา และ Internet/AI ใช้ไม่ได้ โดยไม่ให้เริ่มจ่ายจากคำสั่งเก่าหรือข้ามเงื่อนไข
- วัดเวลาจากเหตุหยุดจนปั๊มและน้ำหยุดจริง รวมปริมาณไหลต่อ เพื่อกำหนดเกณฑ์ยอมรับและแก้ทางน้ำก่อนยืนยันความปลอดภัย

แนวทางความปลอดภัยยืนยันแล้ว ส่วนรายละเอียดวงจร ขีดจำกัด วิธีทดสอบ และเกณฑ์ยอมรับยังต้องกำหนดตามอุปกรณ์จริง รายการข้างต้นยังไม่ใช่ผลทดสอบหรือข้อสรุปว่าผ่าน M7


## ลำดับประกอบและทดสอบเสนอ

ใช้ `TEST_RECORD_TEMPLATE.md` บนเครื่องสำหรับบันทึกรายครั้งและสถานะ PASS/FAIL/BLOCKED เกณฑ์ตัวเลขที่ยังไม่กำหนดห้ามถือว่าผ่าน

บันทึกรุ่น, serial/variant, เครื่องมือ, ผลวัด, วันที่และผู้ทดสอบทุกขั้น หยุดและแก้เมื่อไม่ผ่าน ค่าเวลา/น้ำหนักด้านล่างต้องกำหนดจากการทดลองและข้อจำกัดจริงก่อน release

1. **ไฟดับและแห้ง:** ตรวจรูยึดจริง, clearance และฉนวน; ตรวจ continuity, polarity, ไม่มี short; แยกภาคน้ำและไฟ ปุ่ม NC ต้องเปิดวงจรด้วยมิเตอร์
2. **ภาคจ่ายไฟไม่มีโหลด:** วัด adapter และ buck ทั้งไม่มีโหลด/โหลดจำลอง ตรวจ 5 V, ripple, อุณหภูมิและการป้องกันก่อนเสียบบอร์ด จากนั้นวัด peak ภายใต้ Wi-Fi และเสียง; ไม่ต่อ USB พร้อมไฟภายนอกจนทราบวงจร power-path
3. **เซนเซอร์:** ตรวจ pinout/แรงดันก่อนต่อ; calibrate load cell หลายจุดในช่วงแก้ว+น้ำและทดสอบซ้ำ, โหลดเยื้องศูนย์, drift และตรวจถอดสาย; level ทดลองผ่านผนังขวดจริงในระดับต่าง ๆ; TDS/อุณหภูมิเทียบ reference และบันทึกความคลาดเคลื่อน; microphone ทดสอบข้อมูลจริง
4. **กำลังปั๊มแยกน้ำ:** ใช้โหลดจำลองก่อน ต่อปั๊มตามแบบที่ยืนยันแล้ว วัดกระแสเริ่ม/ทำงาน/ผิดปกติและพิกัดสาย/ฟิวส์; สั่งหยุดและทดสอบไฟดับ/boot/reset/watchdog/สายควบคุมขาด/stop pressed โดยปั๊มต้องไม่เริ่มเอง
5. **ทางน้ำ:** ใช้น้ำสำหรับทดสอบในบริเวณแยกไฟ ตรวจรั่วตามข้อต่อ ตำแหน่งหัวจ่าย การระบายอากาศและการถอดล้าง; วัดหยด/น้ำไหลต่อหลังหยุดและ siphon หลายระดับน้ำ ห้ามใช้ดื่มจนตรวจวัสดุและสุขลักษณะ
6. **interlock:** ทดสอบแก้วขาด/ยกแก้วระหว่างจ่าย, น้ำต่ำ, sensor ค้าง/ขาด, timeout, node stale, API/network ขาด, รีบูต, กด stop และคืนไฟ บันทึกเวลาและปริมาตรหลังคำสั่งหยุดแต่ละครั้ง ตั้งขีดจำกัดยอมรับก่อนทดสอบ ห้ามรีสตาร์ตเองหลัง fault ต้องตรวจเงื่อนไขและสั่งเริ่มใหม่
7. **ปริมาณ:** ทดสอบหลายเป้าหมายและระดับน้ำ ทำซ้ำเทียบเครื่องชั่งอ้างอิง บันทึก mean/min/max และ error รวม overshoot; จำกัดปริมาณต่ำกว่าความจุแก้วโดยเผื่อ overshoot ที่วัดได้ ไม่มี flow sensor อิสระ เครื่องชั่งอาจถูกมือแตะหรือเซนเซอร์ค้าง จึงต้องตรวจ plausibility และ timeout ไม่ถือว่าเป็น redundant flow protection
8. **ระบบร่วม:** เปิดเครื่อง → node ส่งค่าจริง → gateway ตรวจ freshness → dashboard อ่าน raw data → มีแก้ว → คำสั่งผ่านขอบเขต → จ่ายและหยุด → บันทึกผล → แจ้ง fault จำลอง; ทดสอบ cloud ล่มให้การหยุดปั๊มยังทำงานในเครื่องและตรวจการกู้คืนข้อมูล
